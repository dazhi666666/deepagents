# Mars native experiment integration

This local integration mounts native Harness participants, configurable role creation, the platform experiment lifecycle, differentiated physical capabilities, Agent-authored tasks, persistent text records and the independent Viewer API. The whole mission and role directory are available at startup and the task journal begins empty. Both `mission_read` and `mars_catalog` expose current creation permissions, role responsibilities and tool lists. Single-Agent instructions explicitly describe sole ownership of all physical work.

Install an isolated profile with `python3 integrations/ai4science/mars/install.py --home <private-home> --directory <fresh-run> --mode environment`, then supervise it with `python3 integrations/ai4science/mars/run.py --home <private-home> --profile mars-environment --no-proxy`. Agent modes use `--mode single-agent` or `--mode multi-agent`, and profiles `mars-single-agent` or `mars-multi-agent`. The supervisor accepts a private `--credentials-file`; the installer accepts key environment names, a route pool and physical direct-interface settings.

One MarsWorld transaction stores laboratory stages, robot trajectories, cargo, crop condition, samples, resource consumption and environmental events. The role-scoped structured tools bind scientific processing to actual Agent-authored tasks and platform experiment requirements. Live observations, historical archive retrieval, note edits, mailbox receipts and verified artifact reads use persisted facts.

The authenticated loopback API exposes snapshots, tasks, objectives, records, paged history, artifacts, events, SSE and checkpoint frames. The separate frontend implements its own rendering. Current capability flags declare crop simulation, trajectories, assessment, checkpoint saving, supervised restoration and human assistance. Each concrete objective is checked against current evidence; invalid ancestry and revoked artifacts affect dependent goals.

The supervisor restores verified consistent checkpoints for observed transport or upstream failures from the current run, branch and epoch. Errors left by discarded branches are audited without triggering another restore. Each model request records its recovery checkpoint, published before charging the next logical decision step. Restoring that checkpoint removes the failed request's environmental advancement. Legacy audit entries use an earlier checkpoint or the explicitly restored baseline. Startup waits for the configured physical IPv4 interface to return, recording network availability outside experimental state. Interface loss during connection establishment produces a transport failure for supervised recovery. State is restored at the original absolute path after old owners exit, and the discarded branch is retained. Native root and cold continuable members are rebound through current role policy. Model costs and accepted external assistance remain in an audit journal outside rollback. Viewer frames have their own cursor and branch identity.

Long-running supervisors must be launched in a detached OS session with persistent private output files. If a supervisor exits while its native host remains active, `--adopt-process-group <pgid>` verifies the profile command, listening process group and authenticated run identity before taking over. Adoption preserves the active model requests and current world. Subsequent transport recovery uses the same stopped-host checkpoint procedure.

Provider pool entries may use different HTTPS API origins with the same model name. The physical direct transport accepts `additionalOrigins` containing each extra origin and its public DNS-resolved IPv4 address, sharing the configured physical interface and normal TLS verification. Credentials remain environment references in profiles. Adding a route requires a checkpoint continuation for the active host to load the updated provider registry and private environment. Request and usage accounting remains separated by provider alias.

`report.ts` supplies a stopped-run read-only recomputation profile. New installations generate `mars-evaluate-<mode>` alongside their experiment and recovery profiles. The report verifies native membership, physical operation identity, committed artifact hashes and current objective scores without opening device Providers. Active runtime leases prevent offline evaluation.

The installed historical dataset contains simulated sensor series, maintenance facts, past experiments and versioned documents. Negative logical ticks precede the mission. Historical records support retrieval and planning, while live evidence supplies current experimental outcomes.

Focused verification uses `pnpm exec vitest run --config integrations/ai4science/mars/vitest.config.ts`, `pnpm exec tsc -p integrations/ai4science/mars/tsconfig.json` and `python3 integrations/ai4science/mars/test_supervisor.py`. The supervisor regression simulates interface disappearance and return before the native launch, checking stable settings and owner cleanup. Native integration tests use an explicitly scripted adapter to verify real tools and lifecycle behavior. Real intern-s2 development runs are separately labeled; final repeated comparisons require terminal evidence and matched frozen inputs.

## v0.2 Viewer API and Mission Control

The Viewer API now also serves the Mars panel directly: `/score` (redacted until settlement), `/sensors`, `/telemetry/channels`, `/telemetry?channels=&from=&to=&limit=`, `/deliverables`, `/incident-reports`, `/analysis-runs[/id]`, `/measurements?resultId=`, `/raw/{key}`, `/announcements`, `/evaluation` (403 while running) and `/model-activity`. Human-intervention endpoints were removed. The runtime passes these reads to `startViewer`; the panel reads them only through `/mc/mars/*`, which adds the Viewer bearer server-side.

Two optional panels can run together: `missionControlPorts: { harness, mars }` (legacy `missionControlPort` aliases the harness panel). The harness port now serves the maintained execution dashboard; the Mars port lazily loads this project's panel with authenticated execution and Viewer API upstreams. Each panel has its own token and abort scope and writes its link into `<run>/mission-control.json` as `{ harness?: { launchUrl }, mars?: { launchUrl } }`. Neither panel requires the retired Agent Router server. Work-mail facts remain authoritative and the legacy board JSON is only a display projection. The installer exposes `--mission-control-port` and `--mars-control-port`.

Running scores are redacted by `score-view.ts`: O, observable incident counts, R progress/evidence/deadline and submission quality remain; accuracy A, total S, normalization and truth-derived incident parts do not. `/evaluation` exposes task truth, baselines and per-incident scores only after `status === 'completed'`. `collect-runs.py --runs <runs>` writes the static `runs/index.json` used by the comparison page.
